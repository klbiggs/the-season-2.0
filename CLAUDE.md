# CLAUDE.md — *The Season*

Project memory for future Claude Code sessions. Read this first; it tells you where the real documents live and what the non-negotiable rules are.

## Project at a glance

*The Season* is a single-player, turn-based, browser-based social-strategy and dynasty-simulation game (Regency / early Victorian Britain). A previous implementation is being rewritten greenfield. This repo is the new build.

## Where the source of truth lives

1. **`greenfield-spec.md`** — the only authoritative description of what the game does and why. WHAT and WHY only; no HOW. When the spec and code disagree, the spec wins unless an open question has been resolved in writing.
2. **`plans/MASTER.md`** — the architecture and phase index for the rebuild. Tech stack decisions, cross-cutting contracts, and pointers to per-phase subplans.
3. **`plans/phases/NN-name.md`** — one per phase (P0 through P18). Self-contained — when working on a phase, read its subplan + the relevant spec sections it references; don't try to hold the whole spec in context.

Always reach for the spec and the relevant phase subplan before inferring intent from code.

## Tech stack (locked — do not second-guess)

React 19 + Vite 6 + TypeScript (strict) · Tailwind v4 + shadcn/ui · Zustand + Immer · XState v5 · Dexie (IndexedDB) + Zod migrations · `@google/genai` (Gemini SDK; BYOK, context-cached personas, function-calling for structured output) · Framer Motion · `react-force-graph-2d` for the social web · Biome · Vitest + Playwright · Vercel/Netlify static SPA. **No backend in v1. No PixiJS/Phaser/Three.js. No Tauri/Electron. No Redux. No boardgame.io.** Rationale in `plans/MASTER.md` §2.

## Non-negotiable architectural rules

These come from the spec's §9 "Lessons Learned" plus the master plan §3. Treat them as hard constraints, not preferences.

1. **Pure-logic / orchestrator separation.** `src/game/rules/**` is pure: no imports from UI, persistence, LLM, runtime, or events. Runtime orchestrators wrap pure logic and own all side effects. Lint enforces this (`eslint-plugin-boundaries`).
2. **One canonical tick clock.** A single `tick: number` is authoritative. Every scheduled event stores an **absolute end-tick**, never a relative duration.
3. **Determinism.** No `Math.random()` outside `src/game/rng.ts`. The conversation layer (LLM) is the only non-deterministic subsystem and **must not advance the gameplay PRNG call-count**. The replay harness must produce identical state hashes across 30 runs of any campaign.
4. **Save migrations are named, pure, idempotent functions.** Each `migrate_vN_to_vN+1` lives in its own file with its own Vitest suite. No fall-through migration blocks. No cumulative side effects between migrations.
5. **Action gating is atomic.** Validate preconditions first; deduct resources second; apply effects third. Never deduct-then-error.
6. **Clamp at every mutation site.** Affection/composure/reputation/scandal/favor/hostility/happiness clamping is applied wherever the value is mutated — never only at display.
7. **Async UI mutations.** Every conversation round-trip uses `AbortController` and a `requestId` ref. Post-await mutations check the request hasn't been superseded.
8. **Typed everything.** Discriminated unions for state-machine states, Zod schemas for save versions and LLM responses, typed event publishers. No string-based runtime lookups.
9. **No god files.** Events are partitioned by domain (`runtime/events/scheme.ts`, `events/conversation.ts`, etc.). Views decompose by responsibility, not as monoliths.
10. **Designer constants in one place.** Every numeric tuning (thresholds, costs, durations, decay rates) lives in `src/game/constants.ts`. Identities (NPCs, houses, artifacts, traits) live in `src/game/fixtures/`. Never inline these in UI code.

## Phase discipline

Build in phases per `plans/MASTER.md` §6. P0–P4 are the spine — get determinism, separation, state machines, save migrations, and the LLM round-trip right before fleshing out features.

**When working on a phase:**
- Read that phase's subplan + the spec sections it references — that's enough context.
- Don't pre-implement features owned by a later phase. The phase boundaries are dependency-ordered for a reason.
- Each phase's "Out of scope" list is binding. If something feels missing, it's almost always owned by a later phase.
- Each phase's "Verification" section is the definition of done.

## Coding conventions

- **TypeScript strict mode**, plus `noUncheckedIndexedAccess`.
- **Determinism-sensitive deps are exact-pinned** (no caret). At P0 this is `seedrandom@3.0.5`; later phases that introduce libs whose internals affect hashing (anything participating in `hashableState` or save serialization) must do the same. Other deps may use `~` (patch-only). Document the rationale in a proximity comment when adding to the list.
- **Pure-logic modules return new state**, never mutate. Use Immer at the store/orchestrator boundary, not inside rules.
- **State machines are XState v5 actor refs** held in the Zustand store. Don't inline state-machine logic in components.
- **No comments that paraphrase code.** Comments explain non-obvious WHY — hidden constraints, subtle invariants, references to spec sections. Cite spec section (`§3 "Mood Transitions"`) for rule citations.
- **Tests live next to the code:** `economy.ts` and `economy.test.ts` colocated.
- **Pure-logic test coverage is the determinism contract** — aim for ~100% on `src/game/rules/**`. Coverage on UI is lower priority.
- **No emojis in code or comments** unless the user explicitly asks.
- **`src/game/hash.ts` is the canonical hash module.** Every phase that adds replay-relevant state extends `hashableState`'s projection; `GameStateSchema` (in `src/game/store.ts`) is the single source of truth for what counts as state, and `hashable-state-extension.test.ts` enforces the schema-keys ↔ projection-keys equality. Never compute a side-channel hash.
- **Boundary-rule tests use `ESLint.lintText` against synthetic source strings**, never on-disk `.ts.snippet` fixtures or extension-name games. See `eslint/boundaries.test.ts` for the pattern.
- **Stub-for-anchor.** When a boundary rule needs to reference a file that doesn't have implementation yet, ship the file with `export {};` and a single one-line comment explaining what anchors it (see `src/runtime/tickOrchestrator.ts`). The file existing is the contract.
- **`HouseId` is a branded `string`** (`type HouseId = string & { __brand: "HouseId" }`), exported from `src/game/rng.ts`. Never refer to a house by raw `string`; always cast at the boundary (`"player" as HouseId`) and propagate the type from there. **`CharacterId`, `MarriageId`, `TraitId` (added at P1) follow the same pattern** — branded strings exported from `rng.ts` with companion Zod schemas (`CharacterIdSchema`, etc.) using `.transform`, not `.brand`.
- **Phase-order discipline (P1).** `src/runtime/tickOrchestrator.ts` exports a frozen `PHASES: readonly TickPhase[]` array. Rivals always run last (spec §3); the phase chain order is the determinism contract. Never inline phase logic in components or other modules — substitute via the imported phase functions.
- **Year-pass is a distinct trigger from tick-advance.** Calling `runYearPass()` does NOT advance `tick`. They are two separate store actions with distinct state-mutation effects. Load-bearing for conception cadence, succession entry-point, and replay-harness scheduling.
- **Lex-sort iteration over identifier Maps.** Every rule that iterates a `Map<Id, Entity>` and consumes RNG must sort by Id first (matches the `serializeRegistry` lex-sort discipline from P0). When a rule iterates by house first, it uses lex-`houseId` outer / lex-`characterId` inner. See `src/game/rules/moods.ts` for the canonical pattern.
- **Locked characters skip BOTH the roll AND the draw.** Regression bait — drawing-and-discarding on locked characters silently shifts every other character's downstream draw by one. See `src/game/rules/moods.ts`'s `rollMoodDrift`.
- **Lifespan distribution is `[70, 95]` uniform integer** per `LIFESPAN_RANGE` constant in `src/game/constants.ts` (resolves spec §10 Q18). Future phases extending lifespan via trait modifiers must keep the base distribution intact or bump the save version.
- **Characters / Houses / Marriages are never deleted; status flips only.** `state.characters` grows monotonically across a campaign; death sets `alive: false`, NOT removal. Same for `state.houses` (heirless flag, not removal) and `state.marriages` (`dissolved: true`, not removal). Every `getCharacterOrThrow`-style lookup depends on this invariant.
- **Pure-rule structural-sharing contract.** Rules in `src/game/rules/**` return new state via hand-rolled shallow Map clones (`new Map(state.X)` + `.set(...)` + spread). Never mutate input state or input Maps; never use Immer inside `src/game/rules/**` (Immer is the store/orchestrator boundary, not the rules layer).
- **In-memory `z.map(...)` vs save-format `z.array(z.tuple(...))`.** `GameStateSchema` (in `src/game/entities.ts`) uses `z.map` so rules can call `state.characters.get(...)`. `SaveV3Schema` uses `z.array(z.tuple(...))` for stable on-disk serialization (same form as SaveV1 and SaveV2). The two forms are bridged by `serializeRegistry` / `deserializeRegistry`. Never copy the array shape into the in-memory schema.
- **Save migrations declare an `outputSchema`** matching their target version's `SaveV{to}Schema`. The migration runner Zod-parses each step's output against this schema before the next step runs. A migration that ships without an `outputSchema` is incomplete.
- **Every save migration ships an idempotence Vitest assertion** of the form `expect(migrate(fixture)).toEqual(migrate(fixture))` (via the `assertMigrationIdempotent` helper in `src/persist/migrations/__test-utils__/idempotence.ts`). Catches non-deterministic migrations before they ship.
- **Bare+wrap lifter pattern for additive migrations (P4).** When a migration seeds a new entity (e.g., P4 added the Independent house + 5 NPCs to every legacy save), split the legacy lifter into a private `fromSaveVNBare` (raw deserialization, no seeding) + a public `fromSaveVN` (composes Bare with the seeding helper). The migration then reuses the Bare half (`migrate_vN_to_vN+1 = toSaveVN+1 ∘ seedHelper ∘ fromSaveVNBare`), avoiding the double-seed that would happen if the public wrapper called the seed helper a second time after the migration runner's own seed step. The seeding helper itself MUST be idempotent (checks for the new entity's presence before adding) so the legacy lift + migration runner can both call it safely. See `src/persist/schema.ts:seedIndependentIntoLegacyState`.
- **`SaveLoadError` is the load-path error contract.** All errors thrown by `load()` during a load attempt are instances of `SaveLoadError` and carry a `userMessage: string` field. UI surfaces rendering these errors display `err.userMessage`; the technical `message` is for logging. Programmer-error throws at module-load time (e.g., `assertMonotonic`) are NOT part of this contract — they throw plain `Error` and surface only at test-suite boot.
- **`GameState` fields default to "in schema, in projection, in hash"** unless there is a documented reason otherwise. The `hashable-state-extension.test.ts` enforces schema-keys ↔ projection-keys equality. P2's `campaignName` follows this default (renaming a campaign advances the hash). Excluded-from-hash fields are an exception that requires its own ledger entry in the projection and a `// excluded-from-hash: <reason>` inline comment.
- **Schema↔projection↔selector triple-sync (P3) — extended to QUAD at P6.** Adding a top-level `GameState` field requires updates to FOUR surfaces: `GameStateSchema` (`src/game/entities.ts`), `hashableState` (`src/game/hash.ts`), `selectGameState` (`src/game/store.ts`), AND `overwriteFromGameState` (`src/game/store.ts:overwriteFromGameState`). The trip-wire at `src/game/schema-projection-selector-extension.test.ts` enforces the first three by `Object.keys` comparison; `replace-state.test.ts` exercises the fourth (`overwriteFromGameState` is the write-side mirror called from every `set` body — without the `draft.NEW_FIELD = next.NEW_FIELD` write, every tick-advancing action silently CLEARS the new Map). Also update `createInitialState` and every `set`-style state copy in `store.ts` (`advanceTick`, `runYearPass`, `replaceState`, and every P3+ player-elected action). Forgetting `selectGameState` breaks `save()` silently; forgetting `overwriteFromGameState` writes silently destroys runtime state.
- **Per-iteration multi-Map accumulator pattern (P6).** When a rule walks `Map<Id, Entity>` and EACH iteration may create new whispers/couriers via deterministic-id factories (`makeWhisperId` / `makeCourierPayloadId` that walk `state.whispers.values()` for index counting), the loop accumulator MUST clone-and-write-back EVERY Map that the next iteration's factory reads. `applyStaffOutputsPhase` is the canonical site: clones `acc.rng` (per draw), `acc.staff` (per drift/bribery mutation), `acc.whispers` (per cadence whisper-create), `acc.couriers` (per cadence courier-emit) AND threads `acc` (not `state`) into every factory call. Without this, two same-tick same-(source, subject) creations collide on index 0. See `src/game/rules/staff.ts:applyStaffOutputsPhase`.
- **Terminal-state exile gate is per-action at the rule layer (P6).** When `house.exiled === true`, every player-elected mutation action returns a typed rejection `{ ok: false, reason: { kind: "PlayerExiled" } }` at the TOP of its body, BEFORE any pure-rule call. The gate IS NOT consolidated at the orchestrator because free-action wrappers (P5 `startScheme`/`cancelScheme`, P6 `weaponizeWhisper`/`dismissWhisper`/`assignStaff`/`spymasterIntercept`) don't pass through `advanceTickPure`. Every NEW player action's rejection union must include `| { kind: "PlayerExiled" }`. Exempt actions: `replaceState` (load path), cleanup actions (`exitBallroom`, `abortBallroomRequest`), and `sendBallroomMessage` (gated upstream at `enterBallroom` because `ConversationFailure` uses `reason:` string discriminator incompatible with `{kind}`). Void-returning actions publish `PlayerExileBlocked` to `whisperBus` for debug-trace.
- **Modal-state rule-layer gate principle (P9 generalization of P6).** When a modal state (P6 exile, P9 elopement, future P15 succession crisis) suspends mutation affordances, gate at the rule layer when ANY of: (a) the state persists across save/load, (b) free-action wrappers exist that bypass `advanceTickPure`, or (c) pre-tick mutation precedes `advanceTickPure` in any player-elected wrapper. The earlier "terminal vs transient" framing is superseded by "wrapper-bypass + pre-tick-mutation surfaces." For elopement: every tick-advancing AND free-action wrapper returns `{ kind: "ElopementInProgress" }` (or void-publishes `ElopementBlocked` on `elopementBus`) when `state.elopement !== null`. Every NEW player action's rejection union MUST include `| { kind: "ElopementInProgress" }`. Exempt actions: `replaceState` (load path), the three sprint actions (`elopementPush`/`elopementFreshHorses`/`elopementSurrender`), and the ballroom cleanup actions. `sendBallroomMessage` is gated upstream at `enterBallroom`. **`ElopementBlocked` rides on the per-domain `elopementBus`, NOT `whisperBus`** (deliberate divergence from the P6 PlayerExileBlocked cross-cutting precedent — future modal-state Blocked events follow the per-domain pattern).
- **`pruneOrphanedConversationKeys` extended to modal-state cleanup (P9).** Branch 5 is the FIRST site to route a `state.houses` mutation through the helper. The helper now serves a dual role: (a) death-cascade orphan-prune (branches 1-4), and (b) modal-state cleanup on death (branch 5: state.elopement → null + scandal bump on player house when sprint character dies). Future P11+ death-cascade branches that need cleanup mutations on `state.houses` follow the branch-5 lazy-clone precedent (`let newHouses: Map<HouseId, House> | null = null` + conditional spread in the final return).
- **`pruneOrphanedConversationKeys` is the canonical death-cascade helper (P5/P6).** Every death-mutation path (`applyAgingStep` year-pass deaths, `resolveAssassination` tick-phase deaths, future P8 duels / P11 sibling-rival kills) MUST call this helper. The helper handles conversation-history orphan-prune (P4 origin), affection-map orphan-prune (P4), AND whisper status-flip-to-Dismissed (P6 — Unverified/Verified flip; already-Weaponized whispers persist past subject death per Regency "you can't unprint the news"). `runYearPass`'s store-action wrapper calls `publishWhisperTransitions` (not just `publishCharacterDeaths` per P5) because the year-pass-driven whisper-Dismissed transitions need diff-helper coverage.
- **Bus-event domain partition + 3rd-arg skip-rule pattern (P6).** `publishWhisperTransitions(before, after, wrapperPublishedKeys?: ReadonlySet<string>)` is the canonical diff-helper signature when player-action wrappers also direct-publish their owned events. Wrappers pass `new Set(["weaponize:" + id])` etc.; the diff helper skips matching transitions to prevent double-publish. Tick-advance callers OMIT the 3rd arg (defaults to a module-level `EMPTY_KEYS = new Set()` constant — no per-call allocation). Future domain-event modules (P8 rivals, P11 sibling-rivals) inherit the pattern.
- **Persona prompt format version bump (P6 LLM-cache discipline).** Every change to `buildPersonaPrompt`'s output format MUST bump `PERSONA_CACHE_VERSION` in `src/game/constants.ts`. The version suffix is part of the `CacheKey` shape (`${CharacterId}|${Model}|${version}`) so P4-P5 in-memory caches auto-miss on post-bump lookup; the server-side `displayName` carries the same suffix as defense-in-depth. WITHOUT the bump, returning players hit cached personas missing the new format section AND the LLM emits malformed responses against the stale instruction.
- **Player-elected actions follow the pre-tick action pattern (P3).** All four P3 actions (travel, requestAudience, escapeBankruptcy, refreshWardrobe) mutate `GameState` first via a pure rule function, then call `advanceTickPure` through a store-action wrapper. This guarantees same-tick ordering invariants (notably the §7 audience-drops-rival-hostility-before-rival-phase contract) without orchestrator-internal reordering. New player-elected actions in later phases (P5 schemes, P8 reconciliation) follow this same shape. Rejections are returned as typed discriminated unions (`{ ok: false; reason: SomeRejection }`), never thrown — the UI renders rejection-specific prose.
- **Event-bus is a typed `Map<EventVariant["kind"], Set<Subscriber>>` pub/sub at `src/runtime/events/bus.ts` (P3).** Event types are partitioned per domain (`location.ts`; future phases add `conversation.ts`, `scheme.ts`, etc.). **`bus.publish` fires from store-action wrappers ONLY, AFTER `set` returns** — never from inside the orchestrator's phase chain (which must stay pure) and never from inside an Immer producer body. React subscribers register via the `useBusEvent<K>(bus, kind, handler)` hook (or raw `useEffect` + `bus.subscribe` with explicit cleanup). Future phases inherit this discipline.
- **Deterministic gender derivation via `hashCharIdToGender` (P7).** `src/game/fixtures/hashCharIdToGender.ts` is the FNV-1a 32-bit hash used by BOTH the fresh-state bootstrap path (`buildBaselineNpcCharacter` + `bootstrap.ts` player character) AND the legacy-lift path (`liftLegacyCharactersFromV8Pre` via `seedV8FieldsIntoLegacyState`). The algorithm is FROZEN — any change silently re-rolls every legacy character's gender on next load and breaks v1→v8 chain hash-parity. A future feature that needs to mutate gender MUST bump `SAVE_VERSION_CURRENT` and ship a migration that re-derives deterministically. Golden-output Vitest at `src/game/fixtures/hashCharIdToGender.test.ts` pins the 6 canonical pairs as the contract.
- **`pruneOrphanedConversationKeys` extends to multi-branch shared-accumulator (P7).** P7 added THREE new branches: tutor-assignment prune (nulls `assignedTutorCharacterId` on tutor death), Dull-spouse exposure prune (nulls `dullSpouseExposureStartTick` on Dull-spouse death), and marriage dissolution (flips `marriage.dissolved: true` on EITHER spouse's death — closes the non-head-spouse gap that pre-P7 left dissolved=false indefinitely). Branches 1 & 2 share a single `charactersChanged` flag + `newChars` accumulator (one clone, two writes). Branch 3 uses its own `marriagesChanged` flag + `newMarriages` accumulator. Branch 2 reads from `newChars` (NOT `state.characters`) so a character whose tutor AND Dull spouse both die in one year-pass gets both fields cleared. Future death-cascade extensions (P8 duel deaths, P11 sibling-rival kills) follow this pattern.
- **PHASES + STEPS array discipline (P7).** Tick-phase chain (`src/runtime/tickOrchestrator.ts`) length is 9 post-P7; "rivals always run last" stays at terminal slot. Year-pass STEPS (`src/runtime/yearPass.ts`) length is 4 post-P7 with order `aging → maturation → succession → conception`. New phases add via array-literal edit, NOT via mutation; arrays are `as const` frozen at module load. Test enforcement is via test-side `phaseOrderTracker` function-reference identity (NOT module-load `.length === N` assertions — PHASES is module-private; exporting would break the "frozen PHASES" contract).
- **6/6/6 publisher trio across store wrappers (P7 baseline, P9 add-on, P9-followup truth-up).** All three tick-advancing wrapper groups fire **6 publishers each**, just with different membership:
  - `proposeMarriage` (6): proposalOutcome direct + marriageTransitions + temptationLatchTransitions + characterDeaths + whisperTransitions + elopementTransitions. No schemeTransitions (proposal doesn't invoke scheme resolution).
  - `advanceTick` + the 4 P3 wrappers (`travel`/`requestAudience`/`escapeBankruptcy`/`refreshWardrobe`) (6 each): characterDeaths + schemeTransitions + whisperTransitions + marriageTransitions + temptationLatchTransitions + elopementTransitions.
  - `runYearPass` (6): characterDeaths + whisperTransitions + marriageTransitions + temptationLatchTransitions + childMaturationTransitions + archetypeReclassificationsFromSuccession. No schemeTransitions or elopementTransitions — year-pass STEPS doesn't include scheme-resolution, and the Q4 gate blocks runYearPass when `state.elopement !== null`.
  
  The 4 baseline publishers (marriageTransitions + temptationLatchTransitions + characterDeaths + whisperTransitions) ride on EVERY tick-advancing wrapper. **Pre-P9-followup the 4 P3 wrappers were missing marriageTransitions + temptationLatchTransitions** (P7 drift); the P9 followup fixed this so dissolutions/latch-flips during travel/audience/bankruptcy/wardrobe tick chains emit cleanly. The P9-added `publishElopementTransitions` rides every wrapper EXCEPT runYearPass.
- **Save-format strip-on-emit cascade widens with every Character schema addition (P7).** Each `toSaveV{N}` for N < SAVE_VERSION_CURRENT must strip the new live-CharacterSchema fields before `serializeRegistry(state.characters)`. Two helpers ship: `stripV8AndComposureForV5PreEmit` (drops 2 P4 + 7 P7 fields for V2/V3/V4) and `stripV8CharacterFieldsForLegacyEmit` (drops 7 P7 fields for V5/V6/V7). Symmetric inverse: legacy lifters call `liftLegacyCharactersFromV8Pre` which threads V8 defaults via `defaultV8CharacterFields(c.id)` — gender derived via `hashCharIdToGender(id)`, the OTHER fields constant defaults. The strip-on-emit + lift-on-read pair is the contract; every future Character field addition extends BOTH helpers AND every `toSaveV{N}` emitter for N < new live version.
- **PHASES grows to 10 slots at P8; "rivals always run last" stays at terminal slot.** `applyPatronessErosionPhase` inserts at slot 9 (between happiness drift and rival action); `applyRivalActionPhase` REPLACES the P1 identity stub at slot 10 (was slot 9 pre-P8). Per-rival RNG entries (3 new entries seeded at bootstrap + V8→V9 migration) are consumed by BOTH `applyMoodDriftPhase` (iterates all houses including rivals) AND `applyRivalActionPhase` (1 draw per eligible tick). Cumulative per-rival callCount ≈ 3-4 draws/tick.
- **Fixture-id legacy-emit filter (P8).** When a phase introduces fixture-owned entities (rival houses, rival characters) that didn't exist in prior save formats, `toSaveV{N<live}` MUST filter them out by id-set before emit. Without the filter, round-tripping rival entities through pre-P8 schemas corrupts canonical identity (factionId stripped to default, gender re-derived via `hashCharIdToGender`). P8 ships `RIVAL_HOUSE_IDS_SET` + `RIVAL_CHARACTER_IDS_SET` from `src/game/fixtures/rivals.ts` and applies them at `toSaveV2..V8` emitters + in `stripGrievancesForLegacyEmit` / `stripV6FieldsForLegacyEmit` / `stripExiledForLegacyEmit`. Future phases that add fixture entities follow the same pattern: export an `IDS_SET` from the fixture, filter at every legacy emitter.
- **`.default()` backward-compat shortcut for new schema fields (P8).** New `House` fields (`hostility: 0`, `factionId: "faction-crown"`) and the new `Grievance` field (`defendantCharacterId: null`) use Zod `.default()` so legacy V6/V7/V8 saves missing the fields parse cleanly without a full Pre-shape strip-cascade rebuild. The full strip cascade IS still required for legacy emit (`toSaveV{N}` filter helpers); `.default()` only handles the parse-time backfill on load. Future schema widenings can use either pattern — `.default()` is lighter when the new field has a sensible static default; the strip-cascade approach is heavier but cleaner for fields that need fixture-derived defaults.
- **`tryStartScheme.input.skipWealthDeduction` field-widening pattern (P8).** Optional flag on `StartSchemeInput` (NOT a positional 4th parameter) — preserves the 3-arg signature `(state, ownerHouseId, input)` used by all 10 existing call sites. Rival-owned OpenSabotage passes `true`; player-elected actions omit the field. Future "free this action for some callers" widenings of pure-rule signatures follow the same input-field pattern over arity widening.
- **Per-rival RNG seeding via string-concat (P8).** Per-rival `state.rng[rivalHouseId]` entries derive from `createRngState(\`${campaignSeed}|${rivalHouseId}\`)`. Engine-stable string concatenation is mandatory over arithmetic forms (e.g., `campaignSeed * 31 + hashString(...)`) because JavaScript `*` over 32-bit ints produces engine-sensitive results when operands exceed 2^31. `RIVAL_HOUSE_IDS_SET` module-load assertion guards that no rival id contains `|`. Future per-entity RNG seeding (e.g., P11 sibling-rivals) follows the same string-concat discipline.
- **`pruneOrphanedConversationKeys` 4th branch at P8.** Rival-house associated-character pruning. When a rival-associated character dies, drops their id from `RivalActorState.associatedCharacterIds`. Cumulative `newRivalActors` accumulator (lazy-clone on first match) matches the P7 multi-branch shared-accumulator pattern. Gated on `RIVAL_HOUSE_IDS_SET.has(deadChar.houseId)` so non-rival deaths are zero-cost. Future death-cascade extensions add their own lazy-clone branch.
- **Narrow rival-skip gates in `applyEconomyPhase` + `applySuccessionStep` (P8).** Both gates use `RIVAL_HOUSE_IDS_SET.has(houseId)` — NOT a blanket non-player skip. Independent house must continue to participate in economy decay + succession (4 of 5 baseline NPCs are Dependent-role; a blanket skip would silently break their pre-P8 auto-promotion behavior). Future rival-aware filters follow the narrow-set discipline.
- **Rival-action cooldown burns on ALL outcomes (P8).** `applyRivalActionPhase` writes `lastActionTick = state.tick` unconditionally after dispatch — even when `dispatchRivalAction` returns `Skipped` (e.g., `RaiseFactionTension` picked a capped pair, `OpenSabotage` target dead). Without this, a terminal-skip action deterministically re-picks every cooldown cycle, wedging the rival. The "advance cooldown even on no-ops" matches spec §3 line 404. `computeEffectiveWeights` additionally pre-filters capped-pair `RaiseFactionTension` weight to 0 so the dispatch never picks it in the first place — cleaner UX.

## LLM integration specifics

When wiring `src/llm/`:
- BYOK — user supplies their Gemini API key in the UI; never persist to disk, never log.
- Pre-flight key check is shape-only (`/^AIza/`), no network round-trip. Google API keys conventionally start with `AIza` followed by 35 chars.
- Structured output via function-calling: a single `FunctionDeclaration` named `respond` declared in `tools[].functionDeclarations`, forced via `config.toolConfig.functionCallingConfig: { mode: FunctionCallingConfigMode.ANY, allowedFunctionNames: ["respond"] }`. Validate `response.functionCalls[0].args` with Zod; clamp out-of-range fields defensively.
- Context-cache the per-character persona block via `ai.caches.create({ model, config: { systemInstruction, ttl: "3600s" } })` (explicit, stateful — different from Anthropic's per-message implicit `cache_control`). Subsequent `generateContent` calls pass `config.cachedContent: cache.name`. Cache misses fall back to non-cached prompts.
- Model routing: `gemini-3.5-flash` default; `gemini-3.1-pro-preview` on first-meeting (empty `(houseId, targetCharId)` history).
- 15-second timeout via `AbortController.signal.timeout(15_000)` passed in `config.abortSignal`.
- Failure paths (timeout, network, schema, missing key) must: not advance tick, not call combat resolver, not append to history, re-enable UI, surface banner. All four paths have Vitest coverage.
- Use the Context7 MCP for `@google/genai` SDK details — don't guess.
- **Pin-always-overrides for player-explicit tactic affordances (P4, spec §3 line 70).** When a player pins an explicit intent (`pinnedIntent: Tactic | null`) and the LLM returns a `classifiedTactic`, the resolver returns the pin whenever it is non-null — regardless of whether the model's classification is a valid enum. Spec §3 line 70 is the authoritative reading; line 312's "fall back to pinned" wording is the defensive edge case for when the model returns garbage AND no pin is set. Reverting to "model wins when classification is valid" makes the pin button mechanically a no-op in the >99% common case where the model returns a valid enum, which defeats the player's explicit-intent affordance. See `src/llm/types.ts:resolveTactic` and `src/llm/types.test.ts`.

## Verification expectations

Before declaring a phase or task done:
- `pnpm test` — all Vitest suites pass; deterministic replay harness produces identical hashes.
- `pnpm lint` — Biome clean; boundary-rule clean.
- `pnpm typecheck` — strict TS clean.
- For UI changes: run the dev server and exercise the golden path in a browser. If you can't test the UI, say so explicitly rather than claiming success.
- For LLM-touching changes: exercise all four failure paths (timeout, network, schema, missing key), not just the happy path.

## What not to do

- Don't introduce a backend / Supabase / Convex / auth service "to be safe." BYOK + IndexedDB is the design.
- Don't add a renderer (Pixi/Phaser/Three) for the map or ballroom — they're DOM.
- Don't add abstractions for hypothetical future requirements. Three similar lines beats a premature helper.
- Don't widen scope beyond the active phase's "In scope" list without an explicit user OK.
- Don't write multi-paragraph docstrings or feature-description comments. Code + spec section reference is enough.
- Don't fix a symptom by suppressing it — find the root cause. The "Lessons Learned" in `greenfield-spec.md` §9 enumerate the symptom-suppression patterns to avoid.
