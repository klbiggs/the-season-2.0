# P1 — Tick Engine & Pure Rules

> Part of [The Season Master Plan](../MASTER.md). Prior: [P0 — Foundation](./00-foundation.md). Next: [P2 — Save/Load & Migrations](./02-save-migrations.md).

**Goal.** Implement the fixed-phase-order tick orchestrator, the canonical `Character` and `House` data shapes at their P1-minimal subset, and the first batch of pure rules (economy, mood drift, courier transit lookup, aging, conception cycle skeleton, succession entry-point). Pass P0's 30-run replay harness with real per-tick draws integrated.

This phase is the second spine vertebra: P0 proved the determinism plumbing works with one discarded draw per tick; P1 replaces that placeholder with real seeded draws produced by real rules, and proves the harness still produces identical hashes across 30 runs. No views beyond the existing `<DevApp />` ship here — gameplay surfaces land in P3 onward.

**In scope.**

- **`src/runtime/tickOrchestrator.ts`** (real implementation, replacing P0's `export {}` stub-for-anchor at this file) + **`src/runtime/yearPass.ts`** (wholly new file at P1 — no P0 stub exists). **ESLint element classifications differ:** `tickOrchestrator.ts` is its own file-mode element (`runtime-tick-orchestrator` per `eslint.config.js:13`), while `yearPass.ts` falls under the folder-mode `runtime` element (`eslint.config.js:18`). Both element types permit imports from `game-rules` by default (`default: "allow"`), so the orchestrator's intended dependency on rules-layer code is clean for both. **`yearPass.ts` exports** `runYearPassPure(state: GameState): GameState` composing `applyAgingStep → applySuccessionStep → applyConceptionStep` via left-fold. **`tickOrchestrator.ts` exports** `advanceTickPure(state: GameState): GameState`.

  Fixed phase order per spec §3 ("Tick-Driven Time Advancement"):
  1. **time advance** (tick += 1)
  2. **economy** (bankruptcy-tier deltas)
  3. **courier draining** (P1 stub: no-op — no payloads scheduled yet)
  4. **scheme resolution** (P1 stub: no-op — schemes ship in P5)
  5. **global-event roll** (P1 stub: no-op — events ship in P13)
  6. **mood drift** (15% reroll per active non-locked character)
  7. **rival-house action roll** (P1 stub: no-op — rivals ship in P8)

  Each phase is a pure function `(state: GameState) => GameState`. The orchestrator composes them via left-fold over a frozen ordered array `PHASES: readonly TickPhase[]`. The stubs are real exports (`identityPhase` from `runtime/phases/identity.ts`) — never inline lambdas — so later phases substitute by editing the orchestrator's import list, not by mutating a magic registry. **Why fixed-array composition over runtime registration:** registration-style "register your phase here" patterns are exactly the string-keyed runtime lookup §9 warns against; we want a single typed array the type-checker validates.

  A separate `runYearPass(state: GameState): GameState` function runs the year-pass action atomically. It is **not** part of `tickOrchestrator`'s phase chain — year-pass is a player-elected action triggered separately (spec §3 "a separate 'pass year' action"). Calling `runYearPass` does NOT advance `tick`; the spec is explicit that year-pass and tick-advance are distinct triggers.

  **Store-action wiring (binding, B1-cycle-2).** Both `advanceTick` and `runYearPass` are Zustand store actions wired via the existing `replaceState` action from P0 — **not** via Immer-drafted `set(produce(...))`. The pattern:
  ```ts
  // src/game/store.ts (extended at P1)
  // StoreActions type widens from P0's {advanceTick, replaceState} to add runYearPass:
  type StoreActions = {
    advanceTick: () => void;
    runYearPass: () => void;  // NEW at P1
    replaceState: (next: GameState) => void;
  };

  // Implementations:
  advanceTick: () => replaceState(advanceTickPure(get())),
  runYearPass: () => replaceState(runYearPassPure(get())),
  ```
  where `advanceTickPure(state) => runs the orchestrator's phase chain + tick increment` and `runYearPassPure(state) => runs aging → succession → conception` are pure functions exported from `runtime/tickOrchestrator.ts` and `runtime/yearPass.ts`. **Extending the `StoreActions` type happens in the same atomic commit as the action implementation** — otherwise `<YearPassButton />`'s `store.runYearPass()` call fails typecheck mid-sequence. **Why `replaceState` over Immer:**
  - **Pure-rule contract.** P1's pure rules (`src/game/rules/**`) already return fresh state via hand-rolled shallow Map clones (B10 contract). Re-wrapping the returned `GameState` inside an Immer draft would either (a) double-clone (wasteful) or (b) silently lose the rule's returned value if Immer treats the inner draft mutations as authoritative — both failure modes are subtle and replay-breaking.
  - **Atomic swap matches the load path.** `<LoadButton />` already uses `replaceState(fromSaveV1(save))`; a player action that semantically rebuilds state (year-pass restructures family + house records) is the same shape. Consistent wiring is easier for the next reader.
  - **Updating `advanceTick` is part of P1.** P0's `advanceTick` uses `set(produce(...))` with a discard draw. P1 removes the discard and refactors to `replaceState(advanceTickPure(get()))`. Document the refactor in the P0→P1 contract delta for `store.ts`.

  **Year-pass internal ordering (binding, B13).** `runYearPass` composes three steps in a fixed order via left-fold:
  1. **Aging** (`applyAgingStep`) — increments age, marks deaths from natural causes.
  2. **Succession** (`applySuccessionStep`) — promotes heirs of houses whose head died **this year-pass** or in any prior tick.
  3. **Conception** (`applyConceptionStep`) — fires per-marriage conceptions, using the post-succession household state.

  **Tick is read-only across `runYearPass`'s composition (B3-cycle-19 pin).** None of the three sub-steps mutate `state.tick` — they only read it (e.g., `applyAgingStep` writes `diedAtTick = state.tick` without incrementing). This invariant is what makes the synthetic-state succession test's `diedAtTick === 70` assertion correct given input `tick: 70`. Document inline in `yearPass.ts`'s top-of-file comment so a future refactor that conditionally advances tick (e.g., a "long-year" pass) doesn't silently shift every existing test's expected tick values.

  **Why this order:**
  - **Aging before succession** — a head whose `age + 1 === deathAge` must be marked `alive: false` first so the same year-pass's succession can immediately promote an heir; deferring would leave the house head-less for a full year.
  - **Succession before conception** — a marriage whose head died this year-pass must have the dissolution flag flipped (succession step 4) before conception checks marriage validity; otherwise conception fires on a marriage that's about to be marked dissolved.
  - **Single-pass** — no second-pass re-evaluation. If a heir-promotion in step 2 creates conditions for a step-1 effect (e.g., the newly-promoted heir would die on this year-pass), that's a P1 limitation: deaths and promotions cascade across `runYearPass` invocations, not within one. **Why single-pass:** the alternative (re-run aging after succession) introduces draw-order ambiguity that breaks determinism, and the in-spec impact is empty (the spec doesn't require within-year-pass cascading).

- **`src/game/rules/economy.ts`.** Pure functions:
  - `classifyTier(wealth: number): BankruptcyTier` — `Solvent` (≥ 0), `Hemorrhaging` (`-100 < w < 0`), `Embarrassed` (`-500 < w ≤ -100`), `Ruined` (`w ≤ -500`). Exhaustive `switch` on the discriminated `BankruptcyTier` union elsewhere uses `assertNever`.
  - `applyEconomyPhase(state: GameState): GameState` — for each house, classifies its current tier and applies the per-tick delta: `Solvent` → no-op; `Hemorrhaging` `−2 w, −1 r`; `Embarrassed` `−3 w, −1 r, +1 s`; `Ruined` `−5 w, −2 r, +2 s`. Clamps `reputation` and `scandal` to `[0, 100]` at the mutation site (CLAUDE.md non-negotiable §6). Wealth uncapped.
  - **Tier classification happens once per phase, on entry**, not after each delta. **Why:** a house at wealth `−98` (Hemorrhaging) receiving `−2 w` lands at `−100`, which is still Hemorrhaging by the spec's interval definition (`-500 < w ≤ -100`). If we reclassified mid-phase the boundary case would lose a tick of penalty. Pinning "classify once per tick" matches the spec's "per-tick penalties stack by tier" language and avoids cascading-recompute pitfalls. Vitest coverage for the boundary at `wealth = -100` (stays Embarrassed) and `wealth = -500` (stays Ruined).
  - **Escape-valve action is OUT of scope** at P1 — it's a player-elected action at the rural-estate location (P3 strategy map). The plumbing point — that wealth can move via discrete actions, not just economy ticks — is already proven by year-pass's deductions.

- **RNG identity for all P1 per-character draws (binding contract).** Every per-character draw (mood drift, conception trait inheritance, child `deathAge`, succession promotion) advances the **per-house RNG** at `state.rng.get(character.houseId)`. There is no per-character RNG. Per-house is the only registry that exists (`Map<HouseId, RngState>` from P0) and remains so through every later phase. The orchestrator pattern for any per-character phase is:

  1. Group characters by `houseId`.
  2. **Iterate houses lex by `houseId`** (binding — invisible at P1 with one house, load-bearing at P8 rivals). For each house: read the house's `RngState`, iterate that house's characters in lex `characterId` order, thread the `RngState` through each draw, write the final `RngState` back to `state.rng` exactly once. The houses-then-characters iteration order mirrors `serializeRegistry`'s lex-sort discipline so hash invariance holds regardless of `Map` insertion order.

  **Why house-RNG (not character-RNG):** the save format only stores `Map<HouseId, RngState>` (P0 SaveV1); a per-character RNG would mean a Map<CharacterId, RngState> at save time, multiplying replay-state size and forcing migration thrash on every birth/death. Per-house keeps the determinism contract narrow and the call-count discipline auditable. Trade-off acknowledged: two characters in the same house share a single draw stream, so iteration order matters — already pinned (lex by `characterId`).

- **Pure-rule structural-sharing contract (binding, B10).** Pure rules (CLAUDE.md non-negotiable: `src/game/rules/**` may not import Immer) take `GameState` in and return `GameState` out via **hand-rolled shallow Map clones**. The pattern, used uniformly across `economy.ts`, `moods.ts`, `aging.ts`, `conception.ts`, `succession.ts`:
  ```ts
  export function applyXPhase(state: GameState): GameState {
    const characters = new Map(state.characters);      // shallow clone — O(n) but new top-level Map
    const rng = new Map(state.rng);                    // shallow clone if any RNG advance happens
    // ... iterate and `characters.set(id, { ...oldChar, age: oldChar.age + 1 })`
    // ... write `rng.set(houseId, newRngState)` after each house's draws complete
    return { ...state, characters, rng };
  }
  ```
  - **No mutation of input `state` or its nested collections.** The clone-then-mutate pattern is structurally pure (the input Map is never written to).
  - **Why hand-rolled instead of Immer:** the boundaries rule disallows `runtime` (which is where Immer lives) from being imported by `rules/**`. Adopting Immer-in-rules would either require boundary changes or a shim layer; neither carries its weight at P1's allocation rates. Revisit when a profile shows GC pressure from per-tick Map cloning.
  - **Why shallow clone, not deep clone:** the per-entity object spread (`{ ...oldChar, age: ... }`) handles depth for the modified entity; unmodified entities retain reference equality, so the orchestrator's down-stream `hashState` projection sees no spurious changes.
  - **One pattern, applied uniformly.** Every rule file follows this contract. A boundary-clean implementation that violates it (e.g., re-using the input Map) is a bug; reviewer should reject in code review. Document the pattern in the first rule implemented (`economy.ts`) and reference it from a CLAUDE.md addition.

- **`src/game/rules/moods.ts`.** Pure functions:
  - `MOODS = ["Receptive", "Defensive", "Distracted", "Jealous", "Grieving"] as const` — exported from `fixtures/moods.ts`, not inlined here.
  - `MOOD_POOL: ReadonlyArray<{ mood: Mood; weight: number }>` — `Receptive 4 / Defensive 2 / Distracted 2 / Jealous 1` (total weight 9). `Grieving` is narrative-only and never appears in this pool (spec §3 "Mood Transitions"). The pool is a frozen array.
  - `MOOD_POOL_TOTAL_WEIGHT = MOOD_POOL.reduce((s, e) => s + e.weight, 0)` — exported as `const` from `fixtures/moods.ts`. **Derived, not duplicated**, so a future tuning that rebalances individual weights doesn't drift the test fixtures. **Weighted-pick algorithm (R4-cycle-19 promoted from tail to body):** single `drawInt(rngState, MOOD_POOL_TOTAL_WEIGHT)` followed by a linear scan through cumulative weights, returning the first mood whose cumulative weight exceeds the drawn integer. **Do NOT** use `pickItem(rngState, expandedPool)` where `expandedPool` is `MOOD_POOL` flattened to a weight-many-copies array (e.g., `[Receptive, Receptive, Receptive, Receptive, Defensive, ...]`) — that produces the same probability distribution but consumes a different number of draws (one vs N), which is a silent replay-breaker.
  - `rollMoodDrift(currentMood: Mood, rngState: RngState, currentTick: number, lockUntilTick: number): { mood: Mood; rngState: RngState }` — pure. If `currentTick < lockUntilTick`, returns the current mood unchanged and DOES NOT advance `rngState.callCount`. **Why:** spec §3 "locked characters skip the roll" — and skipping the roll means skipping the draw, not drawing-and-discarding. If we drew-and-discarded, the lock-respect would still consume a callCount and a `lockUntilTick` regression bug would silently shift every other character's downstream draw by one. Otherwise rolls the gate via `drawNext` and compares against **`MOOD_REROLL_PROBABILITY`** (imported from `src/game/constants.ts`, NOT the literal `0.15` — R11-cycle-24 pin, CLAUDE.md non-negotiable §10 "designer constants in one canonical location each"). On a hit picks from `MOOD_POOL`. Two draws consumed on a hit (one for the gate, one for the pick); one draw consumed on a miss.
  - `applyFauxPasLock(currentTick: number): number` — returns `currentTick + 5` (spec §3: "locks it for five ticks"). Used by future P4 conversation code; P1 ships and unit-tests the helper so the lock-arithmetic is in one place.
  - **Mood-drift iteration predicate (R10-cycle-30 pin):** `applyMoodDriftPhase` skips characters where `alive === false` OR `currentTick < moodLockUntilTick`. **It does NOT filter on `marriageId`, `role`, `archetype`, or any other field** — the seeded head at P1 has `marriageId: null` and would be wrongly skipped by an over-strict predicate, making the replay harness consume zero draws and the hash-equality assertion pass trivially. Pin the predicate as `alive === true && currentTick >= moodLockUntilTick`; everything else is irrelevant to mood drift.
  - `applyMoodDriftPhase(state: GameState): GameState` — iterates characters in a **deterministically-ordered** nested sequence: **houses lex-sorted by `houseId` (outer)**, characters lex-sorted by `characterId` within each house (inner). Pseudo-code (R11-cycle-30 pin):
    ```ts
    const sortedHouseIds = [...state.houses.keys()].sort();
    for (const houseId of sortedHouseIds) {
      let rngState = getOrThrow(state.rng, houseId);
      const sortedCharIds = [...state.characters.values()]
        .filter(c => c.houseId === houseId)
        .map(c => c.id)
        .sort();
      for (const charId of sortedCharIds) {
        const char = getCharacterOrThrow(state, charId);
        // roll mood drift, advancing rngState...
      }
      // write back rngState exactly once per house
    }
    ```
    At P1 with one house the outer loop runs once and the discipline is invisible, but the nested-loop shape is what guarantees lex-by-houseId iteration order at P8+ when multiple houses share the per-tick scan. **Why deterministic order matters:** two characters in the same house draw from the same `RngState`; iteration order determines which character draws which value. Spec §8 demands identical replay; iteration order MUST be hash-invariant. Map iteration order in JS is insertion order, which is unstable across save/load; lex-sort by `characterId` is the canonical projection (matches `serializeRegistry`'s lex-sort discipline in `rng.ts`). **Performance note (S5-cycle-22):** the per-phase lex-sort is O(n log n) per house; at P1 (≤10 characters) negligible. **Add an inline `// revisit at P8 when character counts grow` comment in `moods.ts`** so the future profiling reminder lands with the code, not just in the plan tail.

- **`src/game/rules/aging.ts`** — the year-pass aging step:
  - `applyAgingStep(state: GameState): GameState` — iterates living characters in lex-sorted `characterId` order; for each, increments `age` by 1. **If `age >= deathAge`** (use `>=`, not `===` — S5-cycle-17 pin; the `>=` form is robust against future migrations or trait-modifier paths that could momentarily produce `age > deathAge`), marks `alive = false` and records `diedAtTick = state.tick`. **No PRNG draws** in aging; death is deterministic from the rolled `deathAge` (set at character creation).

- **`src/game/rules/conception.ts`** — the year-pass conception step:
  - `applyConceptionStep(state: GameState): GameState` — iterates **all** marriages in `state.marriages` (lex-sorted by `marriageId` order — R6-cycle-28 clarification: iterate the full Map, filter in-loop). For each marriage applies these in-loop predicates: (i) **`dissolved === false`** (R6-cycle-26 pin — a marriage dissolved earlier this year-pass by `applySuccessionStep` step 4 is filtered here; the year-pass ordering aging → succession → conception puts dissolution before conception, so this filter catches the same-year-pass dissolution); (ii) both spouses are alive; (iii) both are under age 40 (`spec §3 "either parent reaches age 40"` ⇒ neither has hit 40 yet); (iv) `(currentTick - marriedAtTick) > 0 && (currentTick - marriedAtTick) % YEARS_PER_CONCEPTION_CYCLE === 0` (cadence per spec: "every two years" interpreted as "every 2 years **after** the wedding tick — first conception fires at `marriedAt + 2`, not on the wedding tick itself"), conceives one child via `inheritTraits(unionTraits, TRAITS_ALL.filter(t => !unionTraits.has(t)), rngState)`. The `noveltyPool` is constructed at the call site as `TRAITS_ALL` (the 32-entry tuple from `fixtures/traits.ts`) minus the union — pinning this here makes the 4-draw budget reproducible across implementations and reviewers. **Why the `> 0` guard:** the bare `% 2 === 0` predicate fires on offset 0 (wedding tick) which contradicts the spec's "every two years" wording and is narratively odd. The `> 0` guard skips the wedding-tick fire while preserving the every-2-years cadence thereafter. Vitest fixture exercises both: `marriedAt = 100, currentTick = 100` → no conception; `marriedAt = 100, currentTick = 102` → conceives.
  - **Child id-minting (B1-cycle-24 pin).** Each conceived child gets a deterministic `CharacterId` of the form `\`${marriage.id}-child${state.tick}-${nthChildOfMarriageThisTick}\`` — where `nthChildOfMarriageThisTick` is `0` at P1 (conception fires at most once per marriage per year-pass, so the counter is always `0`; carried as an explicit suffix for forward-compatibility with multi-conception phases). **Example:** marriage `"m-001"` conceiving on year-pass with `state.tick = 100` produces child id `"m-001-child100-0"`. **Why deterministic ids:** replay determinism requires identical state hashes across runs; a UUID or counter-based scheme would either drift across runs or require seed-derived bookkeeping in `RngState`. The marriage-id + tick + position scheme is fully reproducible from state alone, no draws consumed. P7 can extend the suffix when conception fires multiple times per cycle.
  - **Child character construction (B2-cycle-24 pin).** The conceived child is added to `state.characters` (Map insertion via shallow-clone, per the structural-sharing contract) with the following defaults: `id` per B1 above; `houseId` per B9 below; `name: STARTING_CHILD_NAME_PATTERN(marriage.id, state.tick)` — a deterministic template like `\`Child of ${marriage.id} @${tick}\`` exported from `fixtures/names.ts` alongside `STARTING_HEAD_NAME`; `birthTick: state.tick`; `age: 0`; `deathAge` rolled via the per-house RNG (1 draw, the 5th of the 5-draw-per-conception budget); `alive: true`; `diedAtTick: null`; `mood: "Receptive"` (no draw — fixed); `moodLockUntilTick: 0`; `role: "Dependent"`; `archetype: "None"` (Q4 stub); `traits` per `inheritTraits` (4-draw budget); `marriageId: null`. P7 will overhaul the name template once the full roster ships.
  - **Child house assignment (B9 pin).** The new child joins **`state.characters.get(marriage.spouseAId).houseId`** — the lex-first spouse's house at marriage creation time. **Why this rule, not "the head's house" or "the mother's house":** at P1 there's only one house and one couple, so any rule is observationally identical. P7 will introduce cross-house marriages where the choice matters; a consistent lex-first rule keeps the determinism contract narrow (no implicit gender encoding, no fragile head-of-house identity tracking) and gives the P7 implementer a fixed extension point. Document inline that `spouseAId` is chosen at marriage construction time as the lex-smaller `CharacterId` of the two spouses — this freezes the assignment regardless of which spouse later becomes head-of-house.
  - **RNG identity for conception draws.** Per the binding RNG-identity contract (above): conception consumes draws from `state.rng.get(spouseAHouseId)` — the same house the child will join. This keeps the child's `deathAge` and `traits` draws on a single RNG stream and the post-conception RngState write-back targets a single house entry.
  - `YEARS_PER_CONCEPTION_CYCLE` lives in `constants.ts` with value `2`. **Naming canonicalization:** the constant is `YEARS_PER_CONCEPTION_CYCLE` everywhere; the earlier-draft `..._IN_TICKS` suffix is retracted. At P1 we fix `1 tick = 1 year` (every tick is a year — there's no faster cadence active at P1; the year-pass action is the only thing that ticks the year-pass timer), so "years per cycle" and "ticks per cycle" coincide numerically — the predicate at the call site reads `(currentTick - marriedAtTick) > 0 && (currentTick - marriedAtTick) % YEARS_PER_CONCEPTION_CYCLE === 0`. **Why we commit tick-resolution here:** the spec is silent on tick→year resolution. Pinning "1 tick = 1 year (P1)" makes year-pass and tick-advance numerically interchangeable, which matters because P1's tick orchestrator advances tick by 1 per `advanceTick()`. If P3 introduces finer tick resolution (e.g., 1 tick = 1 month), it must update this constant AND introduce a separate `_IN_TICKS` constant for tick-arithmetic, but at P1 the single canonical name is correct.
  - `inheritTraits(unionTraits: ReadonlySet<TraitId>, noveltyPool: readonly TraitId[], rngState: RngState): { traits: TraitId[]; rngState: RngState }` — picks 2 from the union (deterministic order: lex-sort the union, draw two indices without replacement); for the third, rolls `< TRAIT_NOVELTY_PROBABILITY` for novelty (pick from `noveltyPool` minus already-chosen) else picks again from union minus already-chosen.
  - **Exact draw budget per call to `inheritTraits` — 4 draws max, deterministic regardless of branch taken:**
    1. First union index → 1 draw.
    2. Second union index → 1 draw.
    3. Novelty gate (`drawNext < TRAIT_NOVELTY_PROBABILITY`) → 1 draw.
    4. Third-trait pick (from novelty pool OR remaining union depending on step-3 outcome) → 1 draw.
    **Total: exactly 4 draws.** No "identity-rng-state draw" — that wording from an earlier plan draft was wrong and is hereby retracted. Every code path consumes exactly 4 draws so the call-count is independent of branching; this matters because branch-dependent draw counts are an immediate replay-breaker. **Implementation order pin (R21-cycle-14):** the novelty gate's `drawNext` (step 3) MUST fire BEFORE the slot-4 candidate-pool is composed. The candidate pool is a pure function of the gate's boolean outcome AND slots 1+2's selections; computing the pool before the gate inverts the dependency and can produce an off-by-one in the novelty path on edge cases.
  - **Empty-pool fallbacks (draw budget preserved, B3-cycle-24 mechanics pinned).** Implementation pattern for each of the 4 slot draws — same shape across all 4:
    ```ts
    // Pseudo-code for one slot's draw (steps 1, 2, and 4):
    const { next, rngState: post } = drawNext(rngState);  // always advances callCount
    rngState = post;
    if (candidatePool.length === 0) {
      // slot stays empty — do NOT push anything to traits[]
      continue;  // proceed to next slot
    }
    const idx = Math.floor(next * candidatePool.length);  // standard drawInt math
    traits.push(candidatePool[idx]);
    ```
    The draw is consumed regardless of pool size; the `next ∈ [0, 1)` value is discarded when the pool is empty. Step 3 (novelty gate) uses `drawNext` similarly — the bool `next < TRAIT_NOVELTY_PROBABILITY` is computed even on empty-pool paths to advance callCount uniformly. **Final `traits.length`** is between `0` (worst case: empty union + empty novelty pool) and `3` (best case: union ≥ 2 + non-empty third pool).
    Vitest covers four input shapes — empty union (0 traits returned, 4 draws consumed); union of size 1 (1 trait returned, 4 draws consumed); empty novelty pool with full union (3 traits all from union, 4 draws consumed); full-union-full-novelty (3 traits, 4 draws consumed) — and **each case explicitly asserts `rngState.callCount` advances by exactly 4** post-call. The callCount-delta assertion is what catches regressions where an "obvious" optimization skips a draw on an empty path.
  - **`pickItem` empty-array contract.** `pickItem` throws `EmptyArrayError` on empty input (per P0). The draw-budget invariant above requires `inheritTraits` to **pre-guard** empty pools — calling `pickItem` on an empty array would throw, not consume a draw. So the implementation uses `drawNext` directly with a pre-checked array length, advancing `callCount` even when the pool is empty (see pseudo-code above).
  - **Lifespan rolled separately, not inside `inheritTraits`.** Each new child rolls `deathAge ∈ [70, 95]` (uniform integer) via `drawInt(rngState, 26)` then adding `70`. **This is an additional draw outside `inheritTraits`'s 4-draw budget; total cost per conception event = 5 draws.** **Resolves §10 Q18 — "Per-character rolled, uniform [70, 95]" is the v1 default.** Trait-modifier extensions are deferred to P7 with the rest of the marriage subsystem; document the deferral here so the P7 implementer doesn't reroll the existing P1 distribution and break replay.
  - **Why iterate marriages in lex-`marriageId` order, not character order:** marriage records may sort differently than their spouse character IDs; a fixed sort key on the marriage entity itself prevents iteration drift if (e.g., P11) re-keys conversation history. `MarriageId` is a branded string analogous to `CharacterId`/`HouseId`.

- **`src/game/rules/succession.ts`** — the year-pass succession step:
  - `applySuccessionStep(state: GameState): GameState` — for each house whose head-of-house character has `alive = false` **AND `house.heirless === false`**, runs heir resolution per spec §3 ("the heir is resolved from the family pool first, then from adult children"). **The `heirless: false` gate enforces idempotence:** a house whose head died at year-pass N with no eligible heir gets `heirless: true` set in step 5 below; subsequent year-passes see that flag and skip the house entirely, preventing duplicate `ancestorSummary` lines and redundant marriage-dissolution writes. The algorithm walks two pools **in order**, taking the first valid candidate:
    1. **Family pool (primary).** Living adult characters in the same house whose role is in the **filter subset `{Spouse, Heir, Dependent}`** (a 3-value subset of the 4-value `Role` enum, deliberately excluding `HeadOfHouse` — the dead head's own role — to enforce implicit self-exclusion). Sort lex by `characterId`; first match wins. Adult = `age >= ADULTHOOD_AGE_IN_YEARS` (= 18). **The filter set is NOT the enum** (R3-cycle-15 clarification): `Role` has 4 values; the family-pool filter is a 3-value subset; the dead head's `HeadOfHouse` is not in the subset → implicit self-exclusion. **Surviving-spouse semantics:** a widowed spouse retains `role: "Spouse"` (the marriage-dissolution step flips the marriage record's `dissolved` flag but does not mutate the character's role); the dissolved-marriage spouse remains eligible for promotion. **Pool-filter order matters:** the role-and-adulthood filter is applied BEFORE step 4's marriage dissolution within `applySuccessionStep`'s composition, so the spouse's role is still `"Spouse"` at filter time regardless of dissolution.
    2. **Adult-children pool (secondary).** Living adult characters in the same house who are direct descendants of the dead head (resolved via child records / parent IDs). **P1 has no child records and no parent-ID tracking on `Character` — those land in P7 alongside the full marriage/conception subsystem.** So at P1, the secondary pool is **always empty by construction**; the function still iterates it (returning an empty list from a helper `findAdultChildren(state, deadHeadId)` that lives in `succession.ts` and is wired to `return []` at P1), so the call-shape and iteration discipline is in place for P7 to fill in. The helper is unit-tested at P1 with a synthetic state asserting it returns `[]` regardless of inputs — guard against drift before P7 wires real logic.
    3. **Sibling-rival promotion of a corpse (§7 edge case):** both pools filter `alive: true`. A sibling who died this same tick (age increment hit deathAge during the year-pass aging step) is `alive: false` and is skipped.
    4. **Marriage dissolution.** Locate the dead head's `MarriageRecord` via `getCharacterOrThrow(state, deadHeadId).marriageId` (the typed lookup helper from `src/game/util/lookups.ts`; bare `state.characters.get(...)` would fail TS strict under `noUncheckedIndexedAccess`). If non-null, fetch the record via `getMarriageOrThrow(state, marriageId)` and — if `dissolved: false` — set `dissolved = true` and `dissolvedAtTick = state.tick`. **Why this step exists at P1 even though remarriage is P7:** spec §3 mandates "the dead head's spouse marriage record is marked dissolved on the surviving spouse so widows can remarry." Without it, P7 will rely on a `dissolved: true` invariant that the P1 data layer never wrote, and any save migrated from a P1-vintage death-event would carry stale `dissolved: false`. Step runs BEFORE promotion so the heir's pre-marriage state (if any) is preserved.
    5. If no candidate exists in either pool, the house enters a `Heirless` terminal state — a flag on the `House` entity. P1 ships this flag; the heirless campaign UX is owned by P7. The succession step itself does not throw or terminate.
    6. On promotion: the heir replaces the dead character in `house.headOfHouseCharacterId`; `generation` increments by 1; `reputation` drops by 20 (spec §3 "new money effect", clamped to `[0, 100]` at the mutation site); an `AncestorSummary` line is appended: `\`G${generation - 1}: ${dead.name} (b. ${birthTick}, d. ${diedAtTick})\``. The heir's `role` becomes `HeadOfHouse`.
    7. **Q4 (mid-life archetype reclassification) resolution:** P1 ships `classifyArchetype(character: Character): Archetype` **at `src/game/fixtures/archetypes.ts`** (B1-cycle-19 pin — colocated with the `ARCHETYPES` tuple it returns from; succession imports it from fixtures, which is allowed by rule (a)'s `game-rules → game-fixtures` permission). The function is a stub returning `"None"` at P1; the classifier is invoked at succession promotion to set the newly-promoted heir's archetype; at P1 it always returns `"None"` so no real reclassification occurs. P7 fills in the real first-match-wins rules per spec §3 "Family Archetype Auto-Classification". **Pinning "No mid-life reclassification" means the classifier is invoked at exactly two trigger points (succession + child maturation, the latter introduced in P7); never on trait acquisition mid-life.** The P1 stub already enforces this by being called from succession only.
  - **Q1 (heirs inherit patroness favor) deferral note.** P1 has no patroness state. When P8 introduces `house.patronessFavor: ReadonlyMap<PatronessId, number>`, succession-time treatment is **inherit** (continuity > reset) per master plan §10 default. P1's `applySuccessionStep` makes no patroness-favor mutation; P8 extends this function (not the orchestrator) when patronesses ship.   **Deliberate divergence from spec §4 on `MarriageRecord` shape (B12 pin).** Spec §4 describes the entity as "Spouse character identifier, married-at tick, dissolved flag, dissolved-at tick, via-elopement flag" — singular "Spouse character identifier" suggests per-character mirrored records (one per spouse, each pointing at their partner). **P1 deliberately uses one record per marriage with paired `spouseAId`/`spouseBId` fields, both spouses' `Character.marriageId` pointing to the same record.** Rationale:
  - **Atomic dissolution.** Spec §3 "the dead head's spouse marriage record is marked dissolved on the surviving spouse" — with a single shared record, one `dissolved = true` write satisfies both sides. Mirrored records would require two writes with an integrity invariant the implementer can violate.
  - **No mirror-drift risk.** Mirrored records can drift (one says `dissolved: true`, the other says `false`) under partial-update bugs. A single record eliminates the class of bug.
  - **Deterministic relationship key.** Lex-sorting `spouseAId, spouseBId` at marriage creation freezes the pair regardless of which spouse later becomes head-of-house — the child-house-assignment rule above depends on this.
  - **Via-elopement flag (deferred).** Spec mentions a `via-elopement` flag; P1 omits it (elopement is P9). When P9 ships, the flag is added to the existing `MarriageRecord` shape and the save format bumps to v3 — no shape-class change required.

  The plan flags this divergence so the spec-vs-code mismatch is intentional and traceable. If a future phase needs to revert to per-spouse mirrored records, the plan must be amended; for now, the single-record form is the canonical P1 shape.

  **Deliberate divergence from spec §4 on `Character.happiness` (omitted at P1).** Spec §4 line 540 lists "a happiness score `[0, 100]`" as a Character field. Rationale: introducing the field at P1 with a constant `100` invites silent drift if P7 implementers expect specific bootstrap semantics. Per the MarriageRecord pattern, the omission is flagged here so the spec-vs-code mismatch is intentional; P7 will bump the save format to v3 to add the field with a defined default.
