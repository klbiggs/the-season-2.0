# P20 — Core-Loop Reachability & Legibility (v1.1 hardening)

> **Status: ✅ done (shipped 2026-05-26).** Track: v1.1 (UI-correctness, no new gameplay rules). Source: [MASTER.md §11.1](../MASTER.md#111-ui-surfacing-gaps-v1-fix-candidates).
> Wires already-built store actions to UI affordances and surfaces already-persisted state. The decisive item is the unreachable `proposeMarriage`; the close second is the buried dynasty clock (`runYearPass`). Without both, the dynasty loop cannot be played through the UI.

## Depends on
P7 (proposal rules + `store.proposeMarriage`, succession, conception), P9 (elopement + `ElopementResolved`), P4 (ballroom + `ConversationResolved`/`FauxPasFired`), P14 (ledger / family tree / social web / TopBar).

## Goal
Make the core dynasty loop **reachable** (the player can marry → conceive → succeed entirely through the UI) and **legible** (endgame-critical scalars and the dramatic payoffs are visible at the point of action).

## Decisions (resolved this session)

These four forks were resolved against the shipped code; the rest of the plan assumes them.

1. **Propose affordance lives in the Ballroom (primary) + Social Web (secondary).** Valid proposal targets are Independent-house NPCs (proposal gates 7/8 reject same-house and non-Independent targets, `src/game/rules/proposal.ts:109-122`), and affection is built/read in the ballroom. `FamilyTreeTab` lists **player-house** members only (`src/ui/ledger/tabs/FamilyTreeTab.tsx:79-81`), so it is the **wrong** home for a propose target — the skeleton's "family-tree rows" suggestion is dropped. The ballroom button is the spine; the Social-Web node action is the convenience surface for a player browsing their affection targets.
   - **SPEC OVERRIDE (resolved in writing this session).** Spec §3 L262 declares the Social Web a "Reading-only view; all mutations happen elsewhere (ballroom, schemes, ledger)," and `src/ui/socialWeb/SocialWebView.tsx:7-8` enforces "Zero mutation affordances" as an invariant citing that line. Adding a propose action to the social web is a **deliberate, authorized deviation** from §3 L262 (per CLAUDE.md "the spec wins unless an open question has been resolved in writing" — this decision is that written resolution). The implementation MUST amend the `SocialWebView.tsx:7-8` invariant comment to record the exception (cite this plan + the decision), so future audits read it as intentional, not a regression. The social web's read-only proposal-**rejection** slide-away (§3 L261, `useSocialWebReactions.ts`) is unaffected and coexists with the new propose action.
2. **Promote + relabel + surface the dynasty clock.** Conception/aging/succession fire **only** in `runYearPass`, today reachable only via the Settings dropdown ("Pass Year", `SettingsMenu.tsx:65-69`). The prominent map button "Stay here a year" actually calls `advanceTick()` (a strategic tick — **no** aging/conception/succession, `LocationDetailsPanel.tsx:112`). P20 adds a first-class **"Pass a Year"** control to the map, **relabels** the tick button so it stops implying a year, and **surfaces a year-pass summary** (births / deaths / succession / generation) computed by a **UI before/after diff** (no new bus events — see decision 4).
3. **Scandal gets a real-threshold cue, not "proximity to exile."** Scandal never directly causes exile in code — exile fires only from Scandal-Sheet self-attribution (`rules/whispers.ts:358`). Scandal's real consequence at a known threshold is patroness favor erosion at `scandal ≥ PATRONESS_FAVOR_EROSION_SCANDAL_THRESHOLD` (= 50, `constants.ts:635`). The TopBar shows scandal as a clamped 0–100 number; at ≥ 50 it flags "censure / patroness displeasure," tied to the actual mechanic. No invented exile-proximity framing.
4. **Golden path verified via Playwright save-injection.** A fresh campaign cannot reach affection ≥ 80 without the LLM, so the propose→accept path is driven in the browser from a pre-seeded high-affection save (via the existing `window.__putRawForTests` DEV seam, `main.tsx:37-42`). No new bus events are introduced — conception/succession surfacing uses a UI state diff, not events (the "no new bus events" cross-cutting constraint holds).

## In scope

Severities carried from §11.1. Each item names its surface + the existing state/action/event it reads.

### CRITICAL — `proposeMarriage` reachable
- **Ballroom propose control.** A "Propose Marriage" affordance on the selected NPC, rendered near `SchemeButtons` in `BallroomView` (free-action sibling, but note: proposal **does** advance a tick via `proposeMarriage`'s wrapper, `store.ts:1531` — unlike schemes). Calls `store.proposeMarriage(selectedTargetId)` and renders the returned `ProposalOutcome` (`rules/proposal.ts:58-66`): an Accepted banner, a roll-rejected banner ("+5 scandal"), and prose for **every** `ProposalRejection` variant (`rules/proposal.ts:42-56` — `TargetTooYoung`, `TargetAlreadyMarried`, `CrossHouseMarriageNotSupported`, `InsufficientAffection {current, required}`, `InsufficientReputation {current, required}`, `PlayerExiled`, `ElopementInProgress`, etc.). Show the current affection vs `AFFECTION_PROPOSAL_THRESHOLD` and house **raw** reputation vs `PROPOSAL_REPUTATION_THRESHOLD` next to the button so the gate is legible **before** the click. The reputation readout MUST read raw `playerHouse.reputation` — gate 12 tests the raw field (`src/game/rules/proposal.ts:143`), NOT the TopBar's effective/artifact-walked `getEffectiveReputation`. Reusing the effective value would misrepresent whether the gate passes (a reputation-boosting artifact can push effective ≥ 40 while raw is < 40).
- **Social-Web propose action (spec-override per Decision 1).** A propose action on Social-Web nodes that are valid affection targets (player-outbound affection edges already render — `src/ui/socialWeb/SocialWebView.tsx`). NOT a one-liner: requires a `ForceGraph2D` `onNodeClick` handler (filtered to target nodes — exclude the player-head hub) plus a React overlay region layered over the canvas to host the shared outcome banner (the canvas itself can't render DOM banners). Reuses the same `ProposalOutcomeBanner` component as the ballroom. Amend the `SocialWebView.tsx:7-8` invariant comment to record the authorized §3 L262 exception. Secondary surface; the ballroom button is the spine.
- **No new rules.** `proposeMarriage` is fully built and tested; P20 only invokes it and renders its return.

### HIGH — legibility of endgame scalars + payoffs
- **TopBar scandal + generation readout.** Add player-house `scandal` (`entities.ts` House field) to `TopBar` (`TopBar.tsx`) beside wealth/reputation, with the ≥ 50 censure cue (decision 3). Add `generation` and a compact `ancestorSummary` affordance (the summary can be a hover/expander — it grows one line per generation, `spec §3 L345`).
- **Elopement Won/Lost outcome surface.** Subscribe to `ElopementResolved` (`runtime/events/elopement.ts:44-52`, carries `outcome`, `marriageMinted`, `reputationDelta`, `scandalDelta`) in **`App.tsx`** — NOT the overlay. The overlay unmounts the instant `state.elopement → null` (`App.tsx:72`), so the outcome banner must live on a surface that persists across the unmount. Render a Won banner (rep-halve / marriage-mint) or Loss banner (+50 scandal) that the player dismisses.

### MEDIUM — ballroom turn legibility + dynasty-clock surfacing
- **Faux-pas surfacing in the ballroom.** Subscribe `BallroomView` to `FauxPasFired` (`runtime/events/conversation.ts:67-73`, carries `targetCharacterId`, `lockUntilTick`, `wasAlreadyLocked`). Show a blunder banner + a per-portrait mood-lock indicator (the target is `Defensive(locked)` until `lockUntilTick`). **Fix the stale `BallroomView.tsx:67-69` comment** (§11.3 item 2 — it claims faux-pas handling that does not exist).
- **Conversation turn-result readout.** Surface `affectionDelta` / `synergy` / `moodHint` from `ConversationResolved` (`conversation.ts:51-60`); today `BallroomView.tsx:72` consumes only `composureDelta`. Add a running affection/standing readout for the selected NPC (reads `state.affectionMap` via `makePairKey(PLAYER_HOUSE_ID, targetId)`) — this doubles as the propose-gate readout above.
- **Year-pass summary (decision 2).** The "Pass a Year" control captures a before-snapshot (`{characterIds, playerHeadId, generation}`), calls `runYearPass`, then diffs the after-state to compose a human summary: new player-house children born, deaths, and on a head change — "succession: Generation N, −20 reputation." Pure UI diff; no new bus events (head death is deliberately suppressed from `publishCharacterDeaths`, `conversation.ts:127-138`, and there is no `ChildConceived`/`SuccessionOccurred` event — confirmed `runtime/events/family.ts` has neither).

## Implementation notes
- **Outcome-rendering component is shared.** Build one `ProposalOutcomeBanner` (maps `ProposalOutcome` → prose, exhaustive `switch` over `ProposalRejection.kind` so TS enforces coverage when a variant is added) and consume it from both the ballroom and the social web. Determinism note: an **Accepted** vs **roll-rejected** outcome both consumed a tick + 1 PRNG draw (`rules/proposal.ts:13-16`); predicate-rejections (gates 1-13) consumed neither — render accordingly (no "tick advanced" implication on a predicate rejection).
- **High-affection save artifact (one construction step).** The golden-path precondition and the acceptance determinism are a **single** artifact, not two open notes. Build it as: `toSaveV1(createInitialState(seed))` (both exist — `src/persist/schema.ts:88` / `src/game/store.ts:145`), then mutate the blob's `affectionMap` to put `makePairKey(PLAYER_HOUSE_ID, target) ≥ 80` and the player house `reputation ≥ 40`, then inject via `window.__putRawForTests("dev", blob)` (`src/main.tsx:41`; the slot MUST be `"dev"` = `DEV_SLOT` so `SettingsMenu.onLoad`'s `load(DEV_SLOT)` reads it) followed by Settings → Load in the browser. Acceptance is probabilistic — slope ≤ 0.95 even at affection 100 (`src/game/rules/proposal.ts:179-185`) — so the same artifact must pin `(seed, callCount)` to a known-accept draw, OR the test re-proposes until accepted (each attempt advances tick + callCount, so the draw changes; P(10 consecutive rejects) ≈ 0). Document the chosen seed/callCount inline in the spec.
- **Faux-pas has no deterministic seam.** `FauxPasFired` publishes from exactly one site — the LLM branch inside `sendBallroomMessage` (`src/game/store.ts:1271-1278`) — so save-injection cannot force it (unlike the propose path). Verify it in a Vitest/component test by publishing `FauxPasFired` directly on `conversationBus` and asserting the `BallroomView` subscriber renders the blunder banner + the per-portrait mood-lock indicator. (`useSocialWebReactions.ts:57-64` is the reference subscriber impl.)
- **"Pass a Year" control placement is pinned to `MapView` top-level**, NOT `LocationDetailsPanel`. The details panel mounts once per current location (`src/ui/map/MapView.tsx:153`) and is location-scoped; a dynasty-clock control belongs at the map level alongside the campaign frame, and placing it in the panel would imply it's a location action. Render it near the map header (a sibling of the active-events chip row) so it reads as a campaign-wide control distinct from "Stay here (advance tick)."
- **Year-pass diff snapshot** is taken synchronously around the `runYearPass()` call in the control's click handler (read `store.getState()` before, call, read after). No subscription needed; the diff is computed once per click.
- **TopBar real estate** is already busy (6 fields). Group scandal next to reputation; put `generation`/`ancestorSummary` as a compact campaign-meta cluster (consider an expander for `ancestorSummary` so it doesn't bloat the bar).

## Verification (definition of done)
- **Playwright golden path (save-injection):** inject a high-affection, reputation-≥-40 save via `window.__putRawForTests` + Settings→Load; enter the ballroom; propose to an adult unmarried Independent NPC; assert an Accepted outcome banner renders; click "Pass a Year" until a child is born (summary asserts a birth) and, after enough years, until succession fires (summary asserts a generation increment). Drives marry → conceive → succeed through the UI alone.
- **Playwright affordance/readout checks:** propose button + affection/reputation gate readout present in the ballroom; TopBar scandal number visible with the ≥ 50 cue; faux-pas banner + mood-lock indicator are verified in Vitest/component by publishing `FauxPasFired` directly on `conversationBus` (no deterministic store seam — see Implementation notes); elopement Won/Lost banner renders after the overlay unmounts.
- **Vitest:** an exhaustiveness test on `ProposalOutcomeBanner`'s rejection `switch` (compile-time `never` guard + a runtime case-per-variant assertion). Year-pass-summary diff helper unit-tested against synthetic before/after states (birth, death, succession).
- All existing Vitest + trip-wire + replay suites pass **unchanged**. `pnpm lint` / `typecheck` / `knip` clean.
