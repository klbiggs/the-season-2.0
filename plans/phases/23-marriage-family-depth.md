# P23 — Marriage, Family & Lifespan Depth (v1.5)

> **Status: ✅ done.** Track: v1.5. Source: [MASTER.md §11.2-B](../MASTER.md#112-v15--deferred-backlog-aggregated-deduped).
> Resolves the deferred §10 marriage/lifespan open questions (Q4/Q16/Q17/Q18) and the family-depth non-goals from P7, and (per this session's decision) builds the full society-dynasty system: society NPCs marry, form sub-dynasties, and a society NPC can be a head-of-house.

## Depends on
P7 (family/marriage/succession), P8 (rivals — for the cross-house alliance cascade + `RIVAL_HOUSE_IDS_SET`), P16 (procedural society), P22 (society replenishment + the Ton view + `dynastySurnameForHouse`/`founderName`).

## Goal
Deepen the family subsystem end to end: marriage reaches across houses (rivals via political alliance, society via love-match), betrothals exist before adulthood, lifespans vary by trait and gender, archetype classification reacts to mid-life change, widows re-enter the marriage market, and the non-player society becomes a living web of sub-dynasties that marry, bear heirs, and succeed.

## Locked design decisions (this session)
1. **Rival marriage = political-alliance path, NOT a love-match.** Rivals stay non-conversable at P23 (conversability + bespoke personas remain P25), so an affection-gated rival marriage would be unreachable. Instead a rival proposal is an *arranged alliance*: gated on house reputation + a wealth **dowry** + a rival-**hostility ceiling** (you cannot ally a rival currently at war), with **no affection requirement**. Acceptance drops that rival's hostility (the alliance bond). Society/Independent marriages keep the existing affection love-match path **unchanged**. Both paths funnel through the single `proposeMarriage` action — the rule routes by the target's house class.
2. **Betrothal = auto-honor at adulthood.** A `Betrothal` entity with a `Pending → Honored | Broken` lifecycle. When both parties are adults (and gates still hold), a year-pass step **auto-mints** the marriage (deterministic, no acceptance roll). Breaking a Pending betrothal is an explicit free action with a scandal cost (and a hostility bump if the jilted party is a rival). **`TargetTooYoung` STAYS** on the *direct* proposal path — betrothal is the *only* pre-adult path; P23 does NOT allow directly marrying a child (spec says "pre-committed to a *future* marriage").
3. **Lifespan = trait-modifier table + gender skew, applied at creation only.** Modifiers adjust the rolled base `[70,95]` at **conception and procedural generation only** — never re-rolling existing characters or fixtures. The `deathAge` schema bound widens to `[DEATH_AGE_MIN, DEATH_AGE_MAX]` to fit modifiers. No new RNG draw (gender + traits are already known when the base offset is rolled; finalization is a deterministic post-adjust).
4. **Tutor reassignment after maturation = NOT added.** Spec §3 L476 ("assignment becomes locked once the child reaches adulthood") is binding; P7's `ChildAlreadyAdult` rejection stays. This skeleton sub-item is dropped as spec-conflicting. The **re-widowing role flip** (the other half of that skeleton bullet) IS in scope.
5. **Society dynasties = FULL build.** Society marriages mint a NEW society `House` (`soc-house-<n>`) with one spouse as `HeadOfHouse`; society conception + succession reuse the existing **house-generic** lifecycle phases (mood drift, conception, succession, economy, aging already iterate `state.houses`). The single-INDEPENDENT-house model is generalized via an `isSocietyHouse(houseId)` predicate (society = not-player, not-rival); INDEPENDENT remains the "unattached singles" pool from which marriages draw.

## In scope

### A. Cross-house marriage — rival political alliance (Q16)
- **Remove the `CrossHouseMarriageNotSupported` gate** (`proposal.ts:117`) and replace gate 8 with **house-class routing** after the incest gate (gate 7, `target.houseId === PLAYER_HOUSE_ID`):
  - `isSocietyHouse(target.houseId)` (INDEPENDENT + minted society houses) → **love-match branch** (existing affection-slope path, unchanged).
  - `RIVAL_HOUSE_IDS_SET.has(target.houseId)` → **alliance branch** (new).
  - else (defensive; no other house class exists) → a residual `{ kind: "TargetHouseInvalid" }` rejection.
- **Alliance branch gates** (after the shared gates 1–7, 9 TargetTooYoung, 10 TargetAlreadyMarried, 11 PlayerAlreadyMarried, 12 reputation ≥ `PROPOSAL_REPUTATION_THRESHOLD`; the affection gate 13 is **skipped** for alliances):
  - **`RivalTooHostile`** — reject if the target rival house's `hostility > ALLIANCE_MAX_HOSTILITY`. You cannot ally a rival actively at war.
  - **`InsufficientWealthForDowry`** — reject if `playerHouse.wealth < ALLIANCE_DOWRY_WEALTH_COST`.
- **Alliance roll + apply** (gates pass → exactly **1 PLAYER-house draw**, same determinism shape as the love-match):
  - Acceptance probability slopes **inversely with hostility**: `ALLIANCE_ACCEPTANCE_FLOOR + (1 − hostility/ALLIANCE_MAX_HOSTILITY) × (ALLIANCE_ACCEPTANCE_CEILING − ALLIANCE_ACCEPTANCE_FLOOR)`, clamped `[0,1]`.
  - **On accept:** mint the marriage (per-character; the rival spouse keeps their own `houseId` — marriage is per-character per spec L335; the union's children join the lex-first spouse's house, which is always the player proposer at v1 — verified: `"player-head"`/`"child-…"` < `"rival-…"`); **deduct the dowry** from player wealth (atomic gating: deduct only on the acceptance path); **drop the target rival's `hostility` by `ALLIANCE_HOSTILITY_DROP`** (clamped `[0,100]` — typically below the activation threshold 25, quieting the rival via the existing `applyRivalActionPhase` gate); flip the target's role `Spinster/Dependent → Spouse`; run the same Dull-exposure detection; write a `proposalsLog` entry.
  - **On reject-on-roll:** `+PROPOSAL_REJECTION_SCANDAL_DELTA` scandal; **no dowry deducted**; `proposalsLog` entry. (Mirrors monarch's-audience "cost paid only on success.")
- **`ProposalOutcome` widening:** the `accepted: true` variant gains `via: "LoveMatch" | "Alliance"` plus optional `allianceHostilityDrop?: number` and `dowryPaid?: number` so the UI renders alliance-specific prose. No new bus event — alliance acceptance reuses `ProposalAccepted` (the hostility drop is a house-state change surfaced by the existing rival ledger; if a discrete cue is wanted, add an `AllianceFormed` variant to `familyBus`, but default is reuse).
- **Reachability — propose affordance on the Ton view.** The player needs a way to select a rival target. Add a **propose-marriage button to `SocietyView` rows** (P22's Ton roster, which already lists all rival + society characters): calls `proposeMarriage(rowCharId)`; the rule auto-routes love-match (society rows) vs alliance (rival rows). Disabled-state tooltips surface the gates (dowry, hostility ceiling, reputation, already-married). This is a **sanctioned mutation affordance on a read roster** (same precedent as P20's authorized Social-Web propose deviation); document it in the `SocietyView.tsx` header.

### B. Pre-adulthood betrothals (Q17) — new `Betrothal` entity + auto-honor
- **New branded id** `BetrothalId` in `rng.ts` (`string & { __brand: "BetrothalId" }`) + `BetrothalIdSchema` (`.transform`, not `.brand`, per the P1 convention) + `makeBetrothalId(state, partyAId, partyBId)` factory (walks `state.betrothals` for the next index — deterministic, **no draw**, same pattern as `makeMarriageId`).
- **New `BetrothalSchema`** (`src/game/entities.ts`, next to `MarriageRecordSchema`):
  ```ts
  export const BetrothalSchema = z.object({
    id: BetrothalIdSchema,
    partyAId: CharacterIdSchema,   // lex-smaller of the two at arrange time
    partyBId: CharacterIdSchema,   // lex-larger
    arrangedAtTick: z.number().int().nonnegative(),
    status: z.enum(["Pending", "Honored", "Broken"]),
    resolvedAtTick: z.number().int().nullable(),       // tick of Honored/Broken; null while Pending
    honoredMarriageId: MarriageIdSchema.nullable(),    // set when Honored
  });
  ```
- **New top-level `GameState.betrothals: Map<BetrothalId, Betrothal>`** — the **only** new top-level field in P23. Full **quad-sync** (CLAUDE.md non-negotiable): `GameStateSchema` + `hashableState` (`serializeRegistry` lex-sort) + `selectGameState` + `overwriteFromGameState`, plus `createInitialState` (empty `new Map()`) and every `set`-style copy in `store.ts`. Trip-wires: extend `schema-projection-selector-extension.test.ts` + add a `betrothals` assertion to `store.replace-state.test.ts`. Save round-trip: in-memory `z.map`, save-format `z.array(z.tuple([BetrothalIdSchema, BetrothalSchema]))` added to the single live `SaveV1Schema` + `toSaveV1`/`fromSaveV1` (pre-release: edit in place, no version bump).
- **New free action `arrangeBetrothal(partyAId, partyBId)`** → `{ ok: true; betrothalId } | { ok: false; reason: ArrangeBetrothalRejection }`. Free (no tick), mirrors `assignTutor`. Gates: modal-state (`PlayerExiled` + `ElopementInProgress` per the CLAUDE.md modal-state gate principle), **exactly one party in `PLAYER_HOUSE_ID`** and the other in a different house (cross-house, society or rival), both alive, neither already betrothed-pending nor married, **at least one party pre-adult** (`age < ADULTHOOD_AGE_IN_YEARS` — if both are adults, the player should just `proposeMarriage`), reputation ≥ `PROPOSAL_REPUTATION_THRESHOLD`. Direct-publishes `BetrothalArranged` on `familyBus`.
- **New free action `breakBetrothal(betrothalId)`** → `{ ok: true } | { ok: false; reason: BreakBetrothalRejection }`. Free. Gates: modal-state + the betrothal exists + status is `Pending`. Effect: flip `status: "Broken"`, set `resolvedAtTick`, `+BETROTHAL_BREAK_SCANDAL` to the player house; if the OTHER party is a rival-house member, `+BETROTHAL_BREAK_RIVAL_HOSTILITY_BUMP` to that rival's hostility (clamped). Direct-publishes `BetrothalBroken`.
- **Marriage-mint helper (extract first).** There is no shared mint helper today — the mint is inlined twice (`applyProposalPure` at `proposal.ts:192-262` and `mintMarriageAndCommit` at `elopement.ts:308`). P23 extracts a single pure `mintMarriage(state, spouseAId, spouseBId, { viaElopement, viaBetrothal }): { nextState; marriageId }` helper (lex-sorts spouses, `makeMarriageId`, writes the `MarriageRecord` + both spouses' `marriageId`, flips the non-head spouse role `Spinster/Dependent → Spouse`, runs Dull-exposure detection) and re-points the proposal accept-branch, the elopement mint, the betrothal honor step, and the society-marriage step at it. This is the shared draw-free mint referenced by items A/B/G.
- **New year-pass STEP `applyBetrothalHonorStep(state): GameState`** (RNG-free, deterministic). For each `Pending` betrothal, when **both parties are alive adults** AND neither is currently married (`marriageId` null or dissolved): **auto-mint the marriage** (via the `mintMarriage` helper above), set `status: "Honored"`, `honoredMarriageId`, `resolvedAtTick`. Apply the same role flips + Dull-exposure detection; if the non-player party is a rival, also apply the `ALLIANCE_HOSTILITY_DROP` (a betrothal honored into a rival house is an alliance too). No dowry on auto-honor (the betrothal was the commitment). **No acceptance roll** — betrothal guarantees the union. Zero draws (id minting + mint helper are draw-free).
- **Auto-break on death.** `pruneOrphanedConversationKeys` gains a betrothal branch: when either party dies, flip any `Pending` betrothal naming them to `Broken` (no scandal — death isn't a jilt), set `resolvedAtTick`. Lazy-clone the betrothals Map (same `??=` pattern as the P9/P11 `state.houses` branches).
- **Proposal interaction.** Add gate **`TargetBetrothedToAnother`** to `proposeMarriage`: reject if the target has a `Pending` betrothal to someone other than the proposer. (A betrothed-to-the-proposer adult is the normal honor path; honor fires at year-pass, so a direct proposal between the betrothed pair is also allowed and simply mints early.)
- **Bus diff publisher `publishBetrothalTransitions(before, after)`** detects `Pending → Honored` and `Pending → Broken` and emits `BetrothalHonored` / `BetrothalBroken`. Rides every tick-advancing wrapper (death-driven auto-break can fire inside assassination/duel resolution) **and** `runYearPass` (auto-honor + aging death). Free-action `breakBetrothal` direct-publishes synchronously, so the next diff pass sees no change (no double-publish; no 3rd-arg skip needed since they are separate store calls).

### C. Trait-modifier + gender-skewed lifespans (Q18)
- **New pure helper `applyLifespanModifiers(baseDeathAge, gender, traits): number`** in a new `src/game/rules/lifespan.ts`:
  `clamp(baseDeathAge + LIFESPAN_GENDER_SKEW[gender] + Σ LIFESPAN_TRAIT_MODIFIERS.get(t), DEATH_AGE_MIN, DEATH_AGE_MAX)`.
- **No new RNG draw — but finalize `deathAge` only after BOTH `gender` AND `traits` resolve, in BOTH paths.** Keep every draw order unchanged (so the harness re-baseline is just the modifier change, not a reorder); roll the **base offset** at the existing deathAge draw, but compute the **final** `deathAge = applyLifespanModifiers(base, gender, traits)` only once gender and the full trait list are known:
  - **conception.ts:** deathAge base = draw 5, gender = draw 6 (traits are draws 1–4, already done). Defer finalization until after the gender draw.
  - **proceduralNpcs.ts:** gender = draw 2, deathAge base = draw 4, but **pooled traits are draws 5–6, AFTER the deathAge draw** (opposite ordering from conception). Finalizing inline at draw 4 would see only `profile.guaranteed` and silently drop the pooled-trait modifiers → wrong `deathAge` (masked by clamp; the dedicated lifespan unit test catches it). So here, finalization must defer to **after the trait loop** (draw 6+), not just after gender.
  - Both paths: roll the base offset at the existing draw site, finalize `deathAge` after the LATER of {gender, last trait draw}. Reorder finalization, not draws.
- **Fixtures are NOT re-derived.** Baseline NPCs, rivals, and the player founder keep their authored `deathAge` (modifiers apply only to *newly generated* characters — conception + procedural + society births). This honors "without silently re-rolling existing characters."
- **Schema bound widening:** `CharacterSchema.deathAge` `z.number().int().min(70).max(95)` → `.min(DEATH_AGE_MIN).max(DEATH_AGE_MAX)`. Existing fixture deathAges (74–85) stay in range. Pre-release: edit the single live schema in place (deathAge predates all save formats — no strip-cascade).
- **Constants (`constants.ts`):** `DEATH_AGE_MIN = 55`, `DEATH_AGE_MAX = 100`; `LIFESPAN_GENDER_SKEW: Record<"Female"|"Male", number> = { Female: +2, Male: -2 }`; `LIFESPAN_TRAIT_MODIFIERS: ReadonlyMap<TraitId, number>` — proposed designer table (values tunable, finalized at convergence): `Rustic +5`, `Sophisticated +3`, `Intellectual +2`, `Pious +3`, `ImpoverishedNobility −5`, `Dull −3`, `Melancholic −4`, `Hedonistic −3`, `Brash −2`. (Trait ids verified against the 33-entry `TRAITS` registry: the correct id is `Hedonistic`, NOT `Hedonist`; `Pious` + the other 7 keys confirmed present.) **Module-load assertion:** every key resolves in `TRAITS_ALL` (assert trait-id validity only; the `[DEATH_AGE_MIN, DEATH_AGE_MAX]` clamp is the value guard).

### E. Re-widowing role flip
- In the death cascade (`pruneOrphanedConversationKeys`, the existing marriage-dissolution branch that flips `marriage.dissolved` on a spouse's death), extend for the **surviving** spouse: if alive and `role === "Spouse"`, **null their `marriageId`** (they are single again — supersedes the P7 "widows keep marriageId pointing to the dissolved marriage" detail; verified safe because the ledger marriage roster reads `state.marriages`, and `isAvailableForRemarriage` already treats null OR dissolved as available), **recompute role** via the maturation role rules (`Female → Spinster`; `Male` + Bohemian-trait → `Bohemian`; else `Dependent`), then **reclassify archetype**. Publish `ArchetypeReclassified` (`trigger: "RoleFlip"`). Lazy-clone characters. This makes widows re-enter the marriage market AND reclassify (a Spinster-role widow with Cunning/Observant becomes a Spymaster — newly useful).
- **Why null the marriageId** (not just flip role): the classifier's Bohemian/Tutor branches gate on `marriageId === null`; without nulling, a male widow flipped to `Bohemian` role would fail the `BohemianRake` archetype branch. Nulling makes the survivor cleanly unwed for the whole classifier.
- **Two-accumulator threading (resolves the R5 hazard).** The existing death-cascade marriage-dissolution branch (`aging.ts:121-138`) flips `marriage.dissolved` via the `newMarriages`/`marriagesChanged` accumulator; re-widowing's survivor write (null `marriageId` + role flip + reclassify) is a `newChars`/`charactersChanged` write — a **second, distinct accumulator** that must fire for the same death. Pin: the survivor id is read from the dissolved marriage record's `spouseAId`/`spouseBId` (the non-dead spouse), and the survivor write reads/writes the **post-branch-1/2 `newChars`** value (so a character touched by an earlier branch in the same death isn't clobbered) — same care as the P7 multi-branch shared-accumulator note. Lazy-clone both Maps.

### F. Random-archetype trait-pool pick at maturation
- `applyMaturationStep` gains an **RNG draw** (supersedes the P7 "Draw budget ZERO" maturation pin): when a maturing character classifies to a **non-None** archetype, roll `MATURATION_RANDOM_TRAIT_PROBABILITY`; on success, grant one random trait from that archetype's `ARCHETYPE_MATURATION_TRAIT_POOL` (deduped against existing traits). Budget: 1 gate draw per non-None-classified maturing char, + 1 pick draw when the gate passes (deterministic given input). None-classified characters draw nothing. This gives un-tutored children some archetype flavor and is independent of the tutor-bonus path (a child can get both).
- **Net-new `rng` accumulator (resolves the R4 hazard).** `applyMaturationStep` today threads ONLY `newChars` + `pendingTutorTraitChoices` (`maturation.ts:51-54`) — it has **no `rng` accumulator**. Item F adds an entirely new `rng` Map clone-write-back to this function. Because maturation iterates lex-`charId` across ALL houses, each draw MUST read/write **`rng.get(c.houseId)`** (the maturing character's own house stream) and write the advanced state back per the per-iteration multi-Map accumulator pattern — never a single shared stream. Add `rng` to the function's return (`{ ...state, characters, pendingTutorTraitChoices, rng }`).

### G. Society dynasties — society marriages + society NPCs as HeadOfHouse
- **`isSocietyHouse(houseId): boolean`** helper = `houseId !== PLAYER_HOUSE_ID && !RIVAL_HOUSE_IDS_SET.has(houseId)`. INDEPENDENT and every minted `soc-house-<n>` are society houses. `SOCIETY_HOUSE_ID_PREFIX = "soc-house-"`. **Home: `src/game/fixtures/rivals.ts`** (resolves to the boundary-clean `game-other` element — `houseName.ts` already value-imports `RIVAL_HOUSES_FIXTURE` from there, so it is UI-importable). Do NOT place it in `rng.ts` (UI value-import of `rng` is banned per the P14 boundary pin).
- **New pure rule `src/game/rules/societyMarriage.ts` → `applySocietyMarriageStep(state): GameState`** (year-pass STEP, RNG-consuming on the INDEPENDENT stream — same stream as replenishment per the P22 coupling note):
  - **Eligible singles:** alive, `age ≥ ADULTHOOD_AGE_IN_YEARS`, `marriageId === null`, `houseId === INDEPENDENT_HOUSE_ID` (the unattached pool — baseline NPCs + procedural society). Lex-sort; split into Female / Male pools (lex-sorted).
  - **Count:** `marriages = min(SOCIETY_MARRIAGES_PER_YEAR, |Female|, |Male|)`. Zero ⇒ zero draws (hash-neutral no-op).
  - **Pairing:** for each of `marriages` iterations, `drawInt(femalePoolRemaining.length)` then `drawInt(malePoolRemaining.length)` (2 draws/pair) to pick the pair; remove both from the remaining pools. Draws from `state.rng[INDEPENDENT_HOUSE_ID]`, write back once at the end.
  - **Per pair → mint a society house:** id `${SOCIETY_HOUSE_ID_PREFIX}${nextIndex}` (nextIndex = count of existing `soc-house-` houses; contiguous, never deleted); **seed `state.rng[socHouseId] = createRngState(`${indepSeed}|${socHouseId}`)`** where `indepSeed = state.rng.get(INDEPENDENT).seed` (deterministic, campaign-specific, no new GameState field for a campaign seed). Build the house via `buildSocietyHouse(houseId, headCharId, factionId)` (faction hash-derived over the **3 non-crown factions** — `faction-court`/`faction-ton`/`faction-country`; NOT the 4-faction set, since `faction-crown` is reserved for player/Independent — for Ton-view color variety; reputation/wealth neutral defaults; all P8–P15 array/counter fields empty/zero like the rival builder). Mint a `MarriageRecord` (lex-sorted spouses). **Move BOTH spouses into the new house** (`houseId = socHouseId`), set `marriageId`, set roles: **Male → `HeadOfHouse`, Female → `Spouse`** (Regency convention; F×M pairing guarantees one of each), and **reclassify** both archetypes.
- **Society conception — free.** `applyConceptionStep` already iterates all marriages and joins the child to `spouseA.houseId` (the society house), drawing from that house's now-seeded RNG. No same-pass conception (`dt = tick − marriedAtTick = 0`). No change needed.
- **Society succession — free.** `applySuccessionStep` already runs for every non-`RIVAL_HOUSE_IDS_SET` house, so a dead society head promotes a society heir (spouse/children) deterministically; heirless society houses get the `heirless` flag; the `−SUCCESSION_REPUTATION_PENALTY` + ancestor-summary apply harmlessly. The PLAYER-only inherited-secrets accumulation is already gated, so society houses skip it. No change needed.
- **Society participation in mood/economy/aging — free + safe.** These phases iterate `state.houses` generically; society houses join automatically. `economy.ts` is **RNG-free** (verified — imports only `PLAYER_HOUSE_ID`), so society-house economy participation is deterministic and harmless (no spurious bankruptcy/exile — exile is scandal-gated and nothing raises society scandal). Mood drift draws from each society house's seeded RNG (entry exists from minting). **No change to these phases.**
- **Maturation Exile gate fix (`maturation.ts:29`).** Today `houseId !== PLAYER && !== INDEPENDENT → "Exile"` would mis-classify *society-house* children as Exile. Widen the non-Exile branch to **all society houses** (`isSocietyHouse`): society + player children get the normal `Spinster/Bohemian/Dependent` rules; the Exile branch becomes truly dead at v1 (kept for synthetic/forward coverage). `findAdultChildren` / succession parent-edge traversal is house-agnostic and needs no change.
